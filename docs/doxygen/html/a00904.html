3. Sensor Fault-Recovery States — Code Derived

This section now covers every STM32 sensor runtime recovery path used by the application:

  • BME680: real three-attempt runtime loop, i2c_recover(I2C1), BME680 I2C/DMA peripheral reinitialization, short backoff and task-level fatal escalation.
  • MPU9250: real three-attempt MPU_readProcessedData() loop, i2c_recover(I2C3), peripheral reinitialization and task-level fatal escalation.
  • MAX31865: real three-attempt temperature conversion, RTD/fault-register validation, spi4_recover(), spi4_restore_and_init(), Max31865_init() and task-level fatal escalation.
  • PMS5003 / PM2.5: actual frame synchronization/checksum validation, no-frame fault threshold, bounded UART1_PM25_Recover() attempts and fatal escalation after the configured recovery budget is exhausted.
  • DS18B20 group: the actual START_CONVERSION -> WAIT_CONVERSION -> READ_AND_PRINT runtime state machine plus its three-stage recovery sequence: OneWire re-arm/reset, rescan/driver re-init, then cold GPIO re-bootstrap/full re-init.

All unrecoverable sensor paths converge on the real task-level fault lifecycle in main.c: mark fault in progress, mark completed, request_iwdg_reset(), then suspend the failed task while the watchdog supervisor owns reset escalation.

8. Multiple Concurrent Fault Injection / Supervisor Coordination — Code Derived

Source basis:

  • .../Core/Src/i2c_dma.c
  • .../Core/Src/iwdg.c
  • .../Core/Src/main.c

This diagram follows the real shared fault-mask and watchdog coordination implemented by system_fault_mark_in_progress(), system_fault_mark_completed(), request_iwdg_reset(), supervisor_check_and_kick() and escalate_to_iwdg_reset().

The critical-fault mask contains six independently tracked owners:

Bit Mask Fault owner
0 0x01 BME680
1 0x02 MPU9250
2 0x04 MAX31865
3 0x08 PMS5003 / PM2.5
4 0x10 DS18B20
5 0x20 ESP32 UART AES-GCM

system_fault_mark_in_progress() ORs the owner bit into system_fault_active_mask and system_fault_in_progress_mask. system_fault_mark_completed() moves that owner out of the in-progress mask and into system_fault_completed_mask.

The first fatal task calls request_iwdg_reset(). On the first request, the implementation records the request timestamp, clears fault_capture_mask, unlocks enrollment, and starts a bounded fault-capture interval. supervisor_check_and_kick() then snapshots the critical active, completed and in-progress masks and ORs newly active owners into fault_capture_mask.

The enrollment window is FAULT_CAPTURE_ENROLL_MS (6000 ms in the supplied implementation). This explicitly allows a second task to enter its own recovery/fatal path after the first task has already requested a reset. The source comments identify this as protection against the "MPU-first/BME-second" race.

Normal completion requires every bit captured in fault_capture_mask to be present in system_fault_completed_mask, no captured owner to remain in system_fault_in_progress_mask, and the enrollment interval to have elapsed. fault_popcount32() then distinguishes single-fault from multi-fault completion. When more than one bit is present, the supervisor calls escalate_to_iwdg_reset("multi fault capture complete").

The hard safety path uses FAULT_CAPTURE_HARD_MAX_MS (12000 ms). If one captured task never clears its in-progress state, the supervisor forces the captured bits to completed, clears their in-progress bits and escalates with "fault capture hard timeout".

During the bounded capture interval the supervisor continues refreshing the IWDG. escalate_to_iwdg_reset() then deliberately stops refreshing it and waits for the hardware watchdog reset. If that reset has not occurred within IWDG_RESET_FALLBACK_MS (3000 ms), the code calls NVIC_SystemReset().

Example from the real bit allocation: capture_mask = 0x18 means bits 0x08 | 0x10 are captured, i.e. PM2.5 and DS18B20 are participating in the same coordinated fault capture.
