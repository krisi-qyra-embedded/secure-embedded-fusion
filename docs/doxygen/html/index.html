System architecture

I built this platform around an STM32F411RE Nucleo and an ESP32. The STM32 handles sensor acquisition, peripheral recovery and encrypted telemetry. The ESP32 validates incoming packets and provides network services through HTTPS and AWS IoT Core.

Firmware execution, telemetry acceptance and watchdog refresh each depend on defined validation checks. Sensor and communication faults pass through bounded recovery attempts before escalation. This connects the security and reliability mechanisms to the actual progress of the application.

Firmware verification and startup

I implemented secure boot using STM32CryptoLib for Ed25519 signature verification and SHA-256 firmware integrity checking. After reset, the bootloader verifies the signed firmware manifest using the public key, then calculates the application hash and compares it with the hash recorded in the manifest.

Both authenticity and integrity checks must pass before execution can continue to the application.

My current implementation stores public and private key material in OTP. Boot verification uses the public key.

Before handing over execution, I validate the initial stack pointer and reset handler address, stop SysTick, clear the interrupt state and configure the application vector table.

I tested the verification stages separately. Firmware changes fail the integrity check, while corruption of the signature or verification public key fails the authenticity check. Either failure blocks application execution.

Each sensor has a dedicated acquisition task. Readings pass through FreeRTOS queues to the telemetry task, which assembles the sensor snapshot for encrypted transmission.

Task synchronization and shared resources

I use binary semaphores to synchronize tasks with DMA completion and error interrupts. Transfers have bounded waits, allowing stalled operations to enter recovery while other tasks continue.

A mutex protects the shared USART2 logging interface so messages from different tasks do not overlap.

Fault recovery and watchdog supervision

For BME680 and MPU9250 I²C faults, recovery starts by stopping DMA, attempting STOP, clearing peripheral errors and checking BUSY. If necessary, I apply SWRST or an APB peripheral reset, restore the configuration and reinitialize the sensor.

Each affected path allows up to three recovery attempts before escalating a persistent failure. Other sensor interfaces use recovery actions appropriate to their peripheral.

The supervisor monitors sensor and communication heartbeats. For monitored DMA sensor paths, driver activity and successful application readings are tracked separately. Transfer completion alone therefore does not establish sensor health.

The independent watchdog runs during normal operation. It is refreshed while the monitored system remains healthy. Exhausted recovery attempts or missed heartbeats eventually stop the refresh and allow the watchdog to reset the STM32.

Authenticated UART transactions

I implemented a full-duplex AES-256-GCM link over USART6 using STM32CryptoLib on the STM32 and mbedTLS on the ESP32.

Each telemetry packet carries a nonce, ciphertext and authentication tag. The ESP32 authenticates and decrypts the packet, then checks its format, replay freshness and parsing before updating the accepted telemetry snapshot.

Responses use encrypted ACK/NACK messages. The STM32 verifies their authentication and matches the response sequence against the outstanding request before acting on them.

Transactions allow up to three attempts, with response timeouts, UART buffer cleanup and a short retry delay. Each new encryption attempt uses a fresh nonce. The request sequence remains unchanged until a valid authenticated ACK with the matching sequence arrives.

Success advances the sequence, refreshes the communication heartbeat and clears the active link fault. Exhausted retries report a fatal communication fault for watchdog escalation.

I preserve nonce state in nonvolatile memory across resets. Receiver freshness checks provide replay detection. Following a watchdog reset, the bootloader repeats firmware verification before restarting the application and communication tasks.

AWS IoT Core integration

The ESP32 connects to AWS IoT Core using MQTT over TLS. The root CA certificate verifies the server, while the device certificate and private key authenticate the ESP32.

The MQTT task combines local ESP32 readings with the latest accepted STM32 snapshot and publishes a JSON payload to the configured topic.

It handles connection retries, keepalive, subscribed messages and reconnection. Its heartbeat is monitored by the ESP32 watchdog supervisor.

Local HTTPS monitoring and OTA

The ESP32 hosts the dashboard HTML, CSS and JavaScript. JSON endpoints update sensor values without reloading the page. TLS uses the configured server certificate and private key.

The dashboard presents local sensor readings and accepted STM32 telemetry. It also provides Wi-Fi configuration, connection status and ESP32 firmware updates through OTA.

Server response failures and task heartbeats are monitored so persistent failures can escalate through the watchdog supervisor.

TLS resource management

I alternate between local HTTPS and cloud MQTT operation to manage the ESP32 RAM required by TLS connections.

When a client connects to the access point, I request an orderly shutdown of the AWS task before starting HTTPS. After the last client disconnects, I wait briefly, stop HTTPS and restart AWS when the station connection is available.

Fault-injection validation

I tested firmware modification, signature and public-key corruption, sensor communication failures, ciphertext and authentication-tag corruption, replayed packets, and counter or session mismatches.

I used runtime logs to check rejection, bounded retries, peripheral recovery, watchdog escalation and startup after reset. The tests exercise both individual validation stages and the recovery paths that connect the two MCUs.
